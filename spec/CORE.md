# UGP Core Specification

## Open Protocol Specification — Working Draft

**Layer:** UGP Layer 2 (Governance) foundation, with constraint binding into Layer 3
**Status:** Draft for public review · Maintained by the UGP Steward (see GOVERNANCE.md)
**Licence:** Apache 2.0 (specification, reference implementations, conformance suite)

> **Scope note.** This document specifies the *open protocol layer* — the compliance token wire format, the verification procedure, the layer model, and the versioning and interoperability rules shared by every UGP sub-protocol. It defines what is transmitted and how it is verified. It does not specify the enforcement mechanisms that generate trust-anchored signatures; those are provided by licensed implementations and are out of scope. The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are interpreted as in RFC 2119.

---

## 1. Purpose

The UGP Core defines the common substrate that all UGP sub-protocols share. Existing protocols carry identity (TLS, OAuth, SAML), authorisation (OAuth, XACML), or platform state (remote attestation). None of them carries **governance process proof**: evidence that a specific output was evaluated against a specific constraint set and refined to satisfy it before release. The UGP fills that gap, and the Core Specification is what makes a token generated under any one sub-protocol verifiable by any UGP verifier.

The Core is **transport-agnostic**. Tokens and messages may be carried over HTTP headers, gRPC metadata, message-queue payloads, or any other transport.

The Core defines how a token is *verified*. How a workload *requests* a governed output from a governing service, and receives the output with its token, is defined in [`EXCHANGE.md`](EXCHANGE.md).

---

## 2. The Layer Model

The UGP is structured in three layers.

- **Layer 1 — Enforcement.** The trust anchor that generates valid, trust-anchored signatures and makes the governance step non-bypassable. Provided by licensed implementations. **Out of scope** for this specification.
- **Layer 2 — Governance.** Token formats, state machines, verification, exchange sequences, and conformance — the Core Specification and the domain sub-protocols. **This layer is open (Apache 2.0).**
- **Layer 3 — Constraint.** The Formal Constraint Specification Language (FCSL), in which a system's rules are expressed. **Open (Apache 2.0).** See [`FCSL.md`](FCSL.md).

The **compliance token** is the bridge between Layer 2 and Layer 1: it is defined openly at Layer 2, but a token carrying a *trust-anchored* signature can only be generated by a Layer 1 implementation. This is the deliberate separation described in [`../GOVERNANCE.md`](../GOVERNANCE.md).

## 3. Terminology

- **Compliance token** — a self-describing record attesting the governance process that produced an output (§4).
- **Governance state** — the complete governance posture of a system: active constraint configuration, fallback tier, convergence parameters, health metrics.
- **Governance-state identifier** — a hash identifying the exact constraint configuration in force.
- **Trust anchor** — the root of trust whose signature appears on a token. The Core treats trust anchors abstractly (see [`TRUST-MODEL.md`](TRUST-MODEL.md)); it does not mandate any particular anchor type.
- **Verifier** — any party that validates a received token.
- **Authority** — a party in the governance trust hierarchy that can vouch for signing keys.
- **Domain / sub-protocol** — a specialisation of the Core for a particular class of governance (AGP, SGP, FA-GP, MA-GP, DLGP, CDP, …).

A full glossary is at [`../GLOSSARY.md`](../GLOSSARY.md).

## 4. The Compliance Token

The compliance token is the fundamental unit of governance interoperability. A token MUST be **self-describing and extensible**: a verifier that does not recognise a domain extension MUST still be able to parse and verify the base fields.

### 4.1 Canonical Wire Format

```json
{
  "ugp_version": "51.0",
  "token_type": "universal_governance_proof",
  "domain": "agp|sgp|fa-gp|ma-gp|dlgp|cdp|custom",

  "governance_state": {
    "identifier": "sha256:...",
    "constraint_set_uri": "ugp://constraints/{domain}/{category}/v{n}",
    "version_counter": 51,
    "authority_signature": "ecdsa-p256:...",
    "domain_extensions": {}
  },

  "convergence_proof": {
    "iterations_executed": 5,
    "divergence_at_entry": 0.847,
    "divergence_at_exit": 0.003,
    "reconciliation_hash": "sha256:...",
    "wcet_bound_satisfied": true
  },

  "output_binding": {
    "output_hash": "sha256:...",
    "timestamp_us": 1735812000000000,
    "hardware_signature": "..."
  },

  "provenance_chain": {
    "previous_token": "sha256:...",
    "ledger_uri": "ugp://provenance/session/..."
  },

  "cross_domain_attestations": [
    { "domain": "sgp", "token_ref": "sha256:..." }
  ],

  "domain_extensions": {}
}
```

### 4.2 Field Requirements

| Field | Requirement | Meaning |
|---|---|---|
| `ugp_version` | MUST | Protocol version the token conforms to (§9). |
| `token_type` | MUST | Identifies the record as a governance proof. |
| `domain` | MUST | The sub-protocol that generated the token. |
| `governance_state.identifier` | MUST | Hash of the constraint set governing the output. |
| `governance_state.constraint_set_uri` | MUST | Resolvable identifier of the constraint set and version. |
| `governance_state.authority_signature` | MUST | Binds the governance state to an authority identity. |
| `convergence_proof` | MUST | Evidence of the refinement process (§4.3). |
| `output_binding.output_hash` | MUST | Binds the token to the exact output it governs. |
| `output_binding.timestamp_us` | MUST | Generation time, Unix epoch microseconds. |
| `output_binding.hardware_signature` | MUST | Non-repudiable signature from the trust anchor. |
| `provenance_chain.previous_token` | SHOULD | Links to the prior token in the session. |
| `cross_domain_attestations` | MAY | References to tokens from other domains (§7). |
| `domain_extensions` | MAY | Self-describing domain-specific fields. |

### 4.3 Convergence Proof Semantics

`convergence_proof` records the refinement process by which the output was brought into compliance.

- `divergence_at_entry` and `divergence_at_exit` are normalised distances (0 = full compliance) before and after governance.
- `iterations_executed` records the number of refinement cycles.
- `reconciliation_hash` binds the refinement record.
- `wcet_bound_satisfied` is a boolean confirming the process completed within its declared worst-case time bound — a mandatory field for any verifier asserting suitability for real-time or safety-critical use.

A token whose `divergence_at_exit` exceeds the constraint set's declared tolerance MUST be treated as a **governance failure**, not a successful attestation.

The word "hardware" in `output_binding.hardware_signature` names the field for historical reasons; the Core treats the signer abstractly as a *trust anchor* (see [`TRUST-MODEL.md`](TRUST-MODEL.md)). What the base format guarantees is that the signature is non-repudiable relative to the asserted anchor; the *strength* of that anchor is an enforcement-layer property outside this specification.

### 4.4 Token Envelope

For transmission, a token MAY be wrapped in an envelope carrying delivery metadata: source and destination system identifiers, session context, and routing information. The envelope is transport-level metadata and is **not** covered by the token's signature.

### 4.5 Serialisation

Implementations MUST produce **canonical, byte-deterministic** serialisation so that cryptographic verification yields identical results across platforms. Conforming implementations MUST agree on field ordering, number formatting, and whitespace per the canonical serialisation rules in the conformance suite. Tokens MAY be compressed, fragmented and reassembled, or batched for constrained or high-throughput transports, provided the canonical form is recoverable for verification.

## 5. Token Verification

A verifier MUST execute the following steps, in order, and MUST define a failure mode for each:

1. **Signature verification** — confirm `output_binding.hardware_signature` is valid for the asserted trust anchor.
2. **Governance-state validation** — confirm `governance_state.identifier` matches the referenced constraint set.
3. **Output binding confirmation** — confirm `output_binding.output_hash` matches the received output.
4. **Freshness check** — confirm the token is neither expired nor replayed (§5.2).
5. **Trust chain resolution** — establish trust in the signing key (see [`TRUST-MODEL.md`](TRUST-MODEL.md)).

Any step's failure MUST cause the token to be rejected with a standardised error code (§5.4).

### 5.1 Partial Verification

A verifier that lacks access to the full constraint set MAY perform **partial verification**: confirming that convergence occurred, that constraints were enforced, and that the trust anchor signed the output, without evaluating the constraint set itself. Partial verification supports privacy-preserving governance, where a system proves it was governed without disclosing its full configuration. A partial verification result MUST be reported as such and MUST NOT be represented as a full verification.

### 5.2 Freshness

Verifiers MUST guard against replay using one or more of: monotonic counters, timestamp bounds, and revocation-list consultation. The acceptable freshness window is a verifier policy and SHOULD be declared during the handshake (§6).

### 5.3 Failure Reporting

Verification failures MUST be reported with standardised error codes indicating the failing step (signature, governance-state, binding, freshness, trust-chain) and SHOULD include remediation guidance. Real-time deployments MAY declare verification latency bounds; verifiers SHOULD support cached and offline verification using pre-distributed trust anchors and delegated verification through a trusted intermediary.

## 6. Handshake and Governance-State Exchange

### 6.1 Handshake and Capability Negotiation

Every interaction between two systems begins with a handshake whose purpose is **governance interoperability** — distinct from transport security (TLS) or authorisation (OAuth). The initiating system advertises: supported protocol versions, available trust-anchor types, active constraint domains, supported token extensions, and current governance-tier state. The parties then select the highest mutually supported protocol version, the strongest mutually trusted anchor type, and the intersection of supported constraint domains, and exchange trust-anchor references sufficient to verify each other's signatures.

Handshake failure MUST be reported with a code identifying the specific incompatibility (version mismatch, no common trust anchor, constraint-domain incompatibility) and recommended remediation. Negotiation outcomes SHOULD be recorded in a tamper-evident audit log.

The handshake establishes interoperability; it is not itself a request for governance. Once a handshake has completed, governed outputs are requested and returned through the Govern exchange of [`EXCHANGE.md`](EXCHANGE.md).

### 6.2 Governance-State Exchange

Beyond per-output tokens, the Core supports continuous exchange of governance **state** for federated and monitored deployments. A governance-state message encodes a system's posture: active constraint-set identifier, fallback-tier state, convergence parameters, governance health metrics (such as divergence-event rates and token-generation rates), and governance-policy version.

Monitoring parties (regulators, auditors, parent organisations) MAY subscribe to state updates with declared frequency, filtering, and access control. Federated deployments SHOULD support **atomic constraint updates** — all federated systems apply a change or none do — and MUST define precedence for conflicting policy updates: **regulatory overrides organisational; organisational overrides system-local.** State messages MAY be transmitted as differentials, MAY use selective disclosure, and MUST include replay protection.

## 7. Cross-Domain Interoperability

Because every sub-protocol produces tokens in the same base format, governance evidence **composes across domains**. `cross_domain_attestations` lets a single token carry, and be verified against, references to tokens from other domains without changing the base format.

A token generated when a model was trained (FA-GP) can be referenced by the inference-time token that governs its outputs (AGP), which can be referenced during multi-agent orchestration (MA-GP), which can sit alongside a security-posture token (SGP). The result is a single, continuous chain of evidence spanning how a model was built, how it behaves, and how it is operated — the continuity that is usually hardest to demonstrate to a regulator and is a native property of the format rather than an add-on.

Because the base format is self-describing and extensible, **new domains add their own attestation fields without breaking existing verifiers**.

---

## 8. Governance Bridges

A **governance bridge** MAY allow systems using non-UGP governance mechanisms to participate by translating their attestations into UGP compliance tokens. Bridged tokens MUST be marked as bridged so that verifiers can apply appropriate trust policy. Cross-organisational federation is supported through mutual-recognition agreements that declare which governance configurations each party accepts from the other.

---

## 9. Versioning and Extensions

The UGP uses **major/minor** version semantics: minor versions MUST preserve backward compatibility; major versions MAY break it. A newer implementation MUST be able to process messages from an older one, and an older implementation MUST gracefully handle unknown extensions (parse-and-verify the base fields).

New token-extension types, constraint-domain bindings, and verification procedures are introduced through a **registered extension framework**. Registration SHOULD pass a defined validation process (compatibility and security review) so the protocol does not fragment into incompatible variants. Deprecated versions and extensions MUST be sunset with a declared transition period.

---

## 10. Conformance

Conformance classes are defined in [`CONFORMANCE.md`](CONFORMANCE.md). In summary, a **Core-conformant** implementation produces and parses tokens in the canonical format of §4, executes the verification sequence of §5, completes the handshake of §6, correctly handles unknown domain extensions, and passes the published conformance test vectors for its declared version. A **generation-conformant** implementation additionally produces trust-anchored signatures via a licensed enforcement layer; a **verification-conformant** implementation need not generate tokens but MUST verify them per §5. Implementations that serve or make governed-output requests may additionally declare **exchange conformance** (see [`EXCHANGE.md` §12](EXCHANGE.md#12-conformance)).
